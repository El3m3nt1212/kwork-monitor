# kwork-monitor

Монитор биржи заказов Kwork: каждые полчаса обходит ленту проектов, складывает каждое наблюдение в SQLite, а в Telegram присылает только те заказы, на которые стоит тратить отклик.

Инструмент сделан для себя, под конкретную задачу: решить, есть ли на бирже работа для новичка и где именно. Работал с 2026-07-24 по 2026-08-18. За это время **1 099 прогонов, 6 590 заказов, 327 тыс. наблюдений** (состояние заказа в каждом прогоне: число предложений, процент найма покупателя, оставшееся время).

Код написан Claude Code. Моя часть — задача, решения по устройству и проверка: каждое правило фильтра проверялось на собранных данных, а не на ощущении.

## Задача

Отклик на Kwork стоит «коннект», а коннектов 30 в месяц. Подходящих заказов в выбранных нишах приходило около двух в неделю при общем потоке около 277 в сутки. То есть задача не «отсортировать ленту», а **«не пропустить редкое и не потратить коннект впустую»**. Отсюда устройство: без моделей и скоринга, но с честным сбором данных, по которым каждое правило фильтра можно проверить.

## Как устроено

```
login_setup.py   разовый вход в аккаунт вручную, сессия сохраняется в профиль браузера
run_once.py      один прогон: полный обход ленты раз в час, между ними лёгкий
   └ scraper.py  Playwright: обход ~42 страниц ленты, разбор карточек
   └ storage.py  SQLite: orders (текущее состояние) + history (каждое наблюдение)
   └ alerts.py   отбор по нишам и порогам → Telegram, один раз на заказ
classify.py      отсев лидогенерации («найдите нам клиентов»)
buyer_history.py досье покупателя по собственным наблюдениям
shortlist.py     ручной отбор: открывает страницы верхушки списка, дочитывает детали
analyze.py       отчёт по базе: время жизни заказов, причины исчезновения
backfill.py      идемпотентный пересчёт старых данных под новые поля
```

## Решения, которые стоило принять осознанно

**Неполный срез не имеет права «хоронить» заказы.** Полный обход дорогой (около 42 запросов), поэтому между полными идёт лёгкий проход по первым страницам. Он ловит новые заказы и обновляет счётчики, но никого не помечает пропавшим: если заказа нет на первых трёх страницах, это ещё не значит, что его нет на бирже.

**Почему заказ исчез — отдельный вопрос, и данные отвечают на него не полностью.** `storage.classify_gone` различает: дожил до дедлайна (никого не наняли), исчез раньше срока поодиночке (вероятный найм или отмена), исчез пачкой в один прогон (событие площадки, а не найм). Страница исчезнувшего заказа просто редиректит на список, поэтому найм от отмены по одной карточке не отличить, и код этого не делает вид.

**Дедлайн восстанавливается, а не угадывается.** Срок приёма предложений заказчик выбирает сам: сутки, двое или трое. Сначала в коде стояла константа 72 часа, выведенная из максимума по 32 наблюдениям. На 6 тыс. заказов «Осталось» при первой фиксации дало три пика (23, 47, 71 ч) с долями 41/33/26%: константа была неверна для трёх четвертей заказов. Исправлено, старые данные пересчитаны `backfill.py` без повторного обхода.

**Лидогенерация отсекается сочетанием, а не списком фраз.** Классификатор ищет рядом глагол получения (найти, привлечь, нужны) и объект (клиент, лид, покупатель) и учитывает порядок слов:

| Текст заказа | Результат |
|---|---|
| Разработать бота для сбора лидов | работа: «сбор» не глагол получения |
| Настроить рекламу для привлечения клиентов | работа: работа названа раньше клиентов |
| Найти 10 клиентов для веб-студии | лидогенерация |
| Привлечь покупателей в интернет-магазин | лидогенерация |

**Гипотезы фильтров проверялись на собранной базе, и часть не выжила.** Пример из `buyer_history.py`: покупатель разместил 15 разнородных заказов одной пачкой под одну цену с «оплачиваемым пилотом», и ни один не закрылся досрочно. Первой гипотезой было текстовое правило «пачка + единая цена + слово „пилот“». Проверка по базе её похоронила: заказы из пачек закрываются досрочно *чаще* фона (41% против 35%), а слово «пилот» встретилось 5 раз на 6 539 заказов. Работает не текст, а собственная история наблюдений: у покупателей, у которых первая половина заказов прошла без досрочных закрытий, во второй половине досрочных 15% против 47% у остальных. Поэтому в оповещении это стоит пометкой с цифрой, а не фильтром. Похожая судьба у фильтра «покупатель ни разу никого не нанял»: на базе его обоснование не подтвердилось, и это записано прямо в докстринге `alerts.py`.

**Скорость обхода подобрана по факту.** При паузе 2,5 с между страницами на 17-й странице выдача начинала приходить пустой, хотя поодиночке страница открывалась. Пауза 4 с, три попытки с отступом, а недогруженный прогон пропускается целиком, а не оседает в истории пустыми строками.

Комментарии в коде объясняют *почему*, с датой проверки факта. Ссылки на файлы вне репозитория (карточки идей, уроки) остались от исходного исследовательского проекта, частью которого был монитор.

## Запуск

```bash
pip install -r requirements.txt
playwright install chromium
python login_setup.py      # войти в Kwork вручную, закрыть окно
python run_once.py         # один прогон; база появится в data/
python analyze.py          # отчёт в data/analysis_snapshot.txt
```

Оповещения в Telegram: положить в `.env` строки `KWORK_TG_TOKEN=...` и `KWORK_TG_CHAT=...`. Для регулярной работы — Планировщик Windows, `pythonw.exe run_once.py` каждые 30 минут.

## Ограничения

- Это личный инструмент для своего аккаунта, с паузами между запросами на уровне чтения глазами. Разметка Kwork проверялась вручную в июле–августе 2026 и могла измениться.
- Тестов нет: правила проверялись на собранных данных (числа выше), а не юнит-тестами.
- Ниши в `alerts.py` соответствуют услугам, которые я тогда выставлял, и меняются вместе с ними.
